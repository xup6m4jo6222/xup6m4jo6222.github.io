# 原型量測：首頁最近專案展示卡的四個變體

量測日期 2026-07-30。方法：`chrome --headless --dump-dom` ＋ 頁面自己把高度寫進 DOM
（沿用 `scripts/verify/field-runtime.mjs` 的「頁面自己回報」手法，回報管道從 HTTP 換成 DOM）。
重跑：`http://localhost:4321/?variant=A&still=1&measure=1`，`<pre id="proto-measure">` 就是結果。

## 「單屏」這條約束比預期緊得多

單位 px。可用高 ＝ 視窗高 − 導覽列 − 頁尾。「差」為正代表溢出。

| 視窗 | 可用高 | 0 現況 | A 有框最近專案展示卡 | B 無框全寬 | C 數字主導 |
|---|---|---|---|---|---|
| 1280×860 桌機 | 665 | **268** ✅ | 831 ❌ +166 | 707 ❌ +42 | **618** ✅ |
| 1280×720 筆電 | 525 | **268** ✅ | 831 ❌ +306 | 707 ❌ +182 | 618 ❌ +92 |
| 375×812 手機 | 621 | **228** ✅ | **620** ✅（差 0） | **513** ✅ | 660 ❌ +40 |

（手機那一列的實際渲染寬是 500px，不是 375——無頭 Chrome 在這台機器上會把 375 鉗成 500，
已知現象，讀手機數字時要記得它比真手機寬。）

## 四個發現

1. **沒有任何一個提案變體在三種視窗都放得下。**只有「現況」到處都放得下，而現況的問題正是它太空。
2. **720px 高的筆電是最嚴苛的一格**——三個提案變體全部溢出。這是最常見的筆電高度，不是邊緣情況。
3. **桌機與手機的排序反轉。**桌機上 C 最好、A 最差；手機上 A／B 放得下、C 溢出。
   成因：手機是單欄，C 的四個數字換行堆高（618 → 660）；而 A／B 的圖變窄也就變矮（831 → 620）。
   **這代表「哪個變體最好」不能只看一種視窗。**
4. **任何含 760×470 比對器的變體都放不進 525px 的可用高度。**比對器縮到內容寬度後高約 433px，
   加上標題與文字就沒有餘裕。要保住「單屏」，比對器必須限高，或者換一個更矮的證據。

## 執行期檢查

四個變體各跑一次**真的演**（不帶 `?still=1`）並攔 console：
`ERROR:CONSOLE` / `Uncaught` / `TypeError` / `ReferenceError` / `SyntaxError` **全部零命中**。

`?still=1` 走的是跟「降低動態偏好」完全同一條分支，所以上面每一次量測同時也驗證了
reduced-motion 的路徑真的能用。

## production 產物檢查

`import.meta.env.DEV` 攔得住標記，但**攔不住 Astro 的樣式抽取**——只要有 `import`，
component 的 `<style>` 就會被抽進 bundle，條件不渲染沒有用。實測第一版漏了一整個
4,830 bytes 的 CSS 檔到 `dist/_astro/`。

修法：`_proto/` 的所有 `<style>` 改成 `<style is:inline>`（Astro 不處理、不打包）。
改完 `dist/` 對 `proto-bar|proto-stage|pa-card|pb-wipe|pc-num|proto-slots` **零命中**，
CSS 檔數從 2 個降回 1 個。

**這件事值得記住**：`import.meta.env.DEV` 只擋渲染，不擋打包。
